# Tool reference

The three MCP tools, their parameters and what they return. For how they work inside, see [how-it-works.md](how-it-works.md); for installation, the [README](../README.md).

| Tool | What it does |
| --- | --- |
| [`literature_search`](#literature_search) | Searches one or more databases, merges and de-duplicates the results, and labels each with its study design. No LLM calls. |
| [`literature_fetch`](#literature_fetch) | Returns full metadata, the whole abstract and the design labels for specific ids. |
| [`literature_fulltext`](#literature_fulltext) | Returns an article's full text as markdown, found through its id or DOI; ChinaXiv and RussiaRxiv texts come as machine translations. Its warning opens with a retraction, notice or expression of concern when the record has one. |

Typical workflow: start with `literature_search`, read promising papers with `literature_fetch`, and use `literature_fulltext` when the abstract isn't enough (methods, dosage, sample sizes). All three are read-only, and refuse a parameter they don't know, so a misnamed one (`databases`, `DOI`) can't be dropped unnoticed.

## `literature_search`

| Parameter | Type | Required | Notes |
| --- | --- | --- | --- |
| `query` | `string` | yes | Search query, not empty, with at least one search term: a query of only punctuation, operators or field tags (`()`, a lone `"`, `*`, `NOT`, `[tiab]`) is refused with `INVALID_INPUT` (a bare `*` matches every record on Europe PMC, 49,330,589 on 2026-11-28, but the tool asks for keywords). 2–5 keywords, not a sentence: PubMed ANDs every space-separated word, so each extra word narrows the result and a long phrase matches nothing. If a query of plain words finds nothing, the warning names the word that blocks it ([Zero results](#zero-results)). An upper-case `OR` joins alternatives on `pubmed` and `europepmc`; ChinaRxiv reads it as a word (see [Databases](#databases)). PubMed field tags (`[tiab]`, `[mesh]`, `[au]`, `[pt]`) apply to `pubmed`. `europepmc` reads `[tiab]`, `[ti]`, `[au]`, `[pt]`, `[ta]`, `[la]`, `[dp]` and `[pmid]`, translated into its own fields, and drops other tags such as `[mh]`, keeping their words, which then match the full text ([Tags on Europe PMC](#tags-on-europe-pmc)). Quote a phrase before its tag (`"sleep apnea"[tiab]`) or tag each word: on `europepmc` an unquoted run of words loses the tag. `chinaxiv` and `russiarxiv` ignore tags. Europe PMC's own syntax, `SRC:PPR` (preprints only) and `TITLE_ABS:word` (also `TITLE:`, `ABSTRACT:`; a tag covers only the next word: `TITLE:a b` is `TITLE:a AND b`, `TITLE:(a b)` needs both in the title), is for `europepmc` alone, since PubMed reads it as words. Europe PMC matches an untagged query against the full text, so papers that only mention the words match too ([how it works](how-it-works.md#the-databases)). |
| `database` | `string \| string[]` | no | `"pubmed"` (default), `"europepmc"`, `"chinaxiv"`, `"russiarxiv"`, an array of these, or `"all"`, in lower case. Any other value is refused. See [Databases](#databases). |
| `maxResults` | `number` | no | Records per database and page: with several databases, a page holds up to `maxResults` from each. Default `10`, max `50`. |
| `abstractMaxChars` | `number` | no | Cut each abstract to at most this many characters (a whole number, `0` or more), at a word boundary and ending in `…`, and set `abstractTruncated: true` on the article. `0` leaves abstracts out; the flag still says the article had one. Default: whole abstracts. A page of 10 full abstracts is roughly 20,000–30,000 characters and `600` halves it, so set one when searching several databases. `literature_fetch` returns the whole abstract. See [Result size](#result-size). |
| `page` | `number` | no | Page, an integer from `1` (default). Page n holds each database's records (n−1)·`maxResults`+1 to n·`maxResults`, in that database's own order. To read on, pass the `nextPage` of the previous result, with the same `maxResults`: another one moves where pages start, so records repeat or are skipped. A page starting past each database's 10,000th record is refused. See [Paging](#paging). |
| `minDesignTier` | `number` | no | Drop results below this design tier (`0`–`5`; `4` = RCTs). Also leaves out every record with a `null` tier (unlabeled records and most meta-analyses and systematic reviews), with a warning. Narrows the query like `studyTypes`, so those records are never fetched. |
| `studyTypes` | `string[]` | no | Keep only these study types. To keep reviews and trials, use this instead of `minDesignTier`. The filter goes into the query (see [Design filters](#design-filters)), so a page holds matching records, short only of those whose tags classify them as another type; a warning then says how many of the fetched records the filter kept, and that `total` and `nextPage` count records before it. `cohort`, `case-control`, `cross-sectional` and `in-vitro` are never assigned from metadata, so filtering on them returns nothing, with a warning. `animal-study` comes only from veterinary publication types: laboratory animal studies aren't labeled with it but flagged `animals-not-humans`, and a search that finds no `animal-study` says so. An empty list means no filter. |
| `dateRange` | `{ from?, to? }` | no | Publication date filter: `YYYY-MM-DD`, `YYYY-MM` or `YYYY` (a year or month covers all of it). `from` or `to` alone leaves the other end open. Applies to every database, and on `pubmed` and `europepmc` matches the electronic publication date too (see [Dates](#dates)). A date that doesn't exist (`2020-13`), or `from` after `to`, is refused. |
| `sort` | `"relevance" \| "date"` | no | `"relevance"` (default): each database's relevance order, re-sorted by design tier when merged. `"date"`: newest first by first publication (the earlier of `pubDate` and `epubDate`), across databases, except that ChinaXiv and RussiaRxiv ignore it (see [Paging](#paging)). PubMed has no such order, so the newest are found among a pool of its issue-date and date-added orders: at least 100 PMIDs of each, more on later pages. |
| `language` | `string` | no | ISO 639-1 hint. Only `chinaxiv` reads it: `"ru"` searches the RussiaRxiv corpus. |

Returns `{ articles, total, totalByDatabase?, query, databases, filters?, page, maxResults, nextPage?, warnings? }`:

- **`articles`**: one record per paper, sorted by design tier (or by date). Each has `id` as its first key: the database's own id, which `literature_fetch` and `literature_fulltext` take. When it is a PMID (all digits: PubMed records, and MEDLINE records on Europe PMC), `pmid` follows it with the same value, and the record is cited as a PMID; any other id (`PPR…`, `PMC…`, `CBA:…`, `chinaxiv-…`, `ru-…`) is cited by `id` with the database, or by `doi` or `url`. (The library's `Article` keeps the id in `id` and has no `pmid`: the tools add `pmid` for a PMID, and `isPmidRecord` tells those records in the library, see [library.md](library.md).) Then `title`, `abstract` (with `abstractTruncated: true` when it is cut, see [Result size](#result-size)), `authors`, `journal`, `pubDate`, `epubDate` (when there is one, see [Dates](#dates)), `doi`, `publicationTypes`, `corrections` (links to a retraction, expression of concern, erratum, newer version or, for a published article, its preprint: see [Preprints and their published versions](#preprints-and-their-published-versions)), and for non-PubMed records `database`, `url` and `language`. ChinaXiv and RussiaRxiv records add `originalUrl`, the record they were translated from; ChinaRxiv returns their authors as one string, which is split into names and cleaned of affiliation markers and repeats, a comma-separated list only where no comma can be part of one name. Every record carries the [study design labels](#study-design-labels): `studyType`, `designTier` and, when any apply, `flags`. MeSH headings are left out to keep results compact; `literature_fetch` returns them.
- **`total`**: the hit counts each database reported, summed, before paging and de-duplication. With a design filter, these count the records the narrowed query matched. A record held by two databases counts twice, so `total` can exceed what the pages hold.
- **`totalByDatabase`**: `{ id: count }`, each database's own count. Only when more than one database was searched; a database that failed is left out, since its 0 would read as a count.
- **`databases`**: the ids searched, in order, including one that failed (a warning says so) and leaving out one a design filter skipped. `[]` when nothing was searched.
- **`filters`**: `{ dateRange?, studyTypes?, minDesignTier? }` as given; absent when the search gave none.
- **`page`**: the page returned.
- **`maxResults`**: the records per database the page holds (the default 10 when none was given). Ask for `nextPage` with it.
- **`nextPage`**: present when some database searched has records past this page; pass it as `page`, with the same `maxResults`, to continue. Absent on the last page.
- **`warnings`**: a database that failed while others answered (its error's message becomes a warning, and the others' results are still returned), records with no tier that `minDesignTier` leaves out, study types below `minDesignTier`, a page the `studyTypes`/`minDesignTier` filter cut short (`The studyTypes/minDesignTier filter kept 1 of the 10 records this page fetched; …`: how many of the fetched records it kept, and that `total` and `nextPage` count records before it), databases a design filter skipped, PubMed records returned without their abstract and retraction links because `efetch` failed, an `animal-study` filter that found none, a ChinaXiv or RussiaRxiv search that matched nothing because of its query rules (one warning naming both when both were searched; the probe warning below replaces it where it applies), a `page` past the last result (it returns no articles), a PubMed search matching over 10,000 records (the count, and how to narrow it: it is served, not refused), PubMed records beyond its 9,999-record limit (narrow the query), a word PubMed found in no record (`PubMed ignored "qzxvbnmk": no record contains it, so it searched without it.`: esearch leaves such a word out of a plain query and searches the rest, without saying so in the records; a term it keeps, whether a quoted word or phrase, a tagged term or an `AND` operand, gets `No PubMed record contains "…".` when the search then finds nothing; a quoted phrase of words that exist, which PubMed holds no phrase for, is searched as its separate words, and the result says `PubMed has no phrase "…", so it searched the words separately: a record need not hold them together.`), and a search that matched no record at all — unless a design filter or a failed database already explains the zero — so a zero is not mistaken for an absence of evidence. For a query of 2–5 plain words that warning names the word that blocks the query (see [Zero results](#zero-results)); otherwise, under a `dateRange`, it names the range (`No record matched the query "…" within dateRange 2020 to 2021. This is not evidence of absence: retry without the dateRange, or with fewer keywords.`), and a one-word query is told to try a synonym, another spelling or another database. When every database searched fails, the tool returns the [error](#errors) instead, so a failed search never looks like an empty one.

PubMed ranks results by relevance differently from one identical request to the next (five identical searches returned five different top-20 lists, 2026-10-20). So that a repeated search returns the same papers, the server reuses a PubMed search's results for an hour.

Titles and abstracts are plain text. PubMed's and Europe PMC's markup (HTML, JATS, MathML) is removed: italics and bold keep their text, character references are decoded (`&#xb1;` → `±`, `&copy;` → `©`), a superscript of digits and signs becomes superscript characters (`10⁻³`, `kg⁻¹`, `³¹P`), subscripts become plain text (`HbA1c`), and the sections of a structured abstract start lines as `LABEL: text`.

### Result size

Whole abstracts make up most of a result: ten PubMed results for four generic queries came to 25,115–28,106 characters of JSON, 12,760–13,330 with `abstractMaxChars: 600` and 6,577–7,154 with `0`; the abstract text alone was about 2,000 characters per record (2026-11-16). `abstractMaxChars` cuts at a word boundary and the `…` counts within the limit. An abstract that fits is left alone. `abstractTruncated: true` also marks a ChinaXiv or RussiaRxiv search preview that ChinaRxiv cut at 500 characters (its search endpoint keeps 497 characters and adds `...`), and that flag is never cleared. `literature_fetch` returns the whole abstract, without the flag.

### Paging

`maxResults` caps each database's share of a page at 50, and `page` reads past it. Each page is merged, de-duplicated by DOI or PMID and sorted (by design tier, or by date) on its own, not together with earlier pages. With `sort: "date"` the newest-first order is global only for PubMed and Europe PMC: ChinaXiv and RussiaRxiv ignore `sort`, so their records come in relevance order and are sorted by date only within their page. A page past the end returns no articles and a warning (`Page N is past the last result…`), also when another database failed (`…of the databases that answered`); `page` `0` or a fraction is refused (the schema rejects it first; `INVALID_INPUT` in library calls).

Paging reaches only the first 10,000 records of a search per database: a page starting beyond them is refused with `INVALID_INPUT` (narrow the query with more specific terms, a `dateRange` or `studyTypes`), and the last page before that limit has no `nextPage`.

- **PubMed** is never refused a query for matching too many records: over 10,000 records, each page of the search carries a warning that names the count and how to narrow the query (`diabetes` matched 1,156,395 records, 2026-11-27). It serves only the first 9,999 records of a search (an `esearch` limit): later pages return no PubMed records and a warning to narrow the query, and the last reachable page carries that warning too. Because its relevance order differs between identical requests, the client takes PMIDs in blocks of 500 from one request and cuts pages from that cached list, extending it with `retstart` when a later page needs more. So within the one-hour cache no page repeats a record, but a record can still be skipped at a 500-record block boundary; with the search cache off (`searchTtlMs` 0), or after its one-hour TTL, pages come from separate requests and can repeat or skip records. With `sort: "date"` the pool of candidates grows geometrically as pages go deeper (up to 9,999 PMIDs of each order) and is rebuilt O(log n) times, so deep date pages cost more requests. Each PMID in the pool needs an `esummary` for its dates (about 2 s per 200), so on the HTTP server a deep date page can run out of its 30 seconds (`TIMEOUT`): the dates already fetched are kept for an hour, so retrying gets further (several tries for the deepest pages). A page past the last record is answered from the counts.
- **Europe PMC** ignores a `page` parameter; the adapter pages with `cursorMark`, remembers the cursors, and reaches a later page cold by walking cheap `idlist` requests.
- **ChinaXiv and RussiaRxiv** page with an opaque ChinaRxiv cursor. A cold later page walks from page 1 with one request per page, against ChinaRxiv's anonymous limit of 30 requests per minute.

### Dates

`pubDate` is the date the database reports, usually the journal issue's (`2019 Apr`). Many papers are published online months earlier; `epubDate` holds that date when the database has it (`2018 Sep 20` from PubMed, `2024-12-16` from Europe PMC). `dateRange` matches either: PubMed's publication date "includes both print and electronic dates of publication, except for electronic publication dates occurring after the print publication date" ([PubMed Help](https://pubmed.ncbi.nlm.nih.gov/help/)), and Europe PMC is queried on a record's first, electronic and print publication dates (`FIRST_PDATE`, `E_PDATE`, `P_PDATE`), as its `[dp]` tag is (see [Tags on Europe PMC](#tags-on-europe-pmc)). So a search for 2024 can return a record with `pubDate: "2025 Jul"` and `epubDate: "2024-12-16"`, and so can a search for 2025: Europe PMC record 39680131 was found for 2025 by the three date fields and not by `FIRST_PDATE` alone (2026-11-16). The order of `sort: "date"` is by first publication whatever the range, so a dated search sorted by date can list a record first published before the range, sorted by that earlier date, as PubMed's can.

### Design filters

`studyTypes` and `minDesignTier` are applied inside the databases that have design metadata. PubMed and Europe PMC are asked only for records carrying a publication type the filter can keep (`"Randomized Controlled Trial"[pt] OR "Equivalence Trial"[pt]` for `randomized-controlled-trial`; `PUB_TYPE:` for Europe PMC), and the [labels](#study-design-labels) are then checked on every record, so a record whose tags classify it otherwise (an RCT also tagged `Observational Study` is `observational`) is still dropped. A search for 20 RCTs on creatine and cognition returns 20 RCTs out of 34 candidates; filtering the plain top 20, as earlier versions did, found 5 (2026-10-20).

Two kinds of filter are narrowed the other way as well, by excluding the publication types of the designs the classifier ranks above: `unknown`, which no tag asks for, and the trial designs below the RCT (`clinical-trial`, `non-randomized-trial`), whose tags PubMed's `[pt]` expands to every RCT (`"Clinical Trial"[pt]` finds 1,065,791 records and 537,751 with `[pt:noexp]`, 2026-11-27). PubMed gets `NOT ("Randomized Controlled Trial"[pt:noexp] OR …)` and Europe PMC `AND NOT (PUB_TYPE:"Randomized Controlled Trial" OR …)`; the list comes from the classifier, so that a record it would keep is never left out (an RCT also tagged `Clinical Trial` is an RCT, but a record tagged `Clinical Trial` and `Review` is a clinical trial, so `Review` stays). PubMed's list is exact. Europe PMC matches a `PUB_TYPE` phrase as a run of words in any type string of a record, and a record carries more than NLM's types: PMC records and MEDLINE records not yet indexed have the publisher's JATS article type (`systematic-review`, `review-article`, `product-review`, …), which the classifier gives no design. `PUB_TYPE:"Review"` finds all of them, and so do `"Systematic Review"` (`systematic-review`, typed alone by Cochrane reviews such as PMID 42803656) and `"Clinical Trial"` (`Clinical Trial Protocol`), so Europe PMC is not asked to leave out those three, and a page there can still hold reviews, systematic reviews and trial protocols that the classifier drops (2026-11-28). The other names are left out only if no type string known to hold their words (the JATS article types, and the strings sampled from Europe PMC) is a different design; a string that no sampled record showed could still be wrongly left out. The same phrase, asked for by `clinical-trial`, would also find the protocols (7 of the 10 records of `tirzepatide apnea`, 2026-11-27), so it is asked for less them: no protocol carries the `Clinical Trial` tag (none of 24,577 in PubMed, 2026-11-27). "creatine cognition" with `studyTypes: ["unknown"]` and `maxResults: 5` returned no articles, with a `total` of 1,521, before; it returns 5, with a `total` of 1,083 (2026-11-27).

Because the query is narrowed, `minDesignTier` never sees the records with a `null` tier that it leaves out, and can't count them: "creatine supplementation" at `minDesignTier: 3` returns RCTs only, with a `total` of 796 of 3,427 records (2026-10-22). The warning says that unrated records were left out whenever `studyTypes` alone would have kept some.

`chinaxiv` and `russiarxiv` records carry no design metadata, so a design filter would drop all of them: those databases aren't searched, and a warning says so. Search them without the filter and read the abstracts.

### Tags on Europe PMC

Europe PMC matches bare words against the full text: `tirzepatide apnea` finds 1,560 records there, and `TITLE_ABS:tirzepatide AND TITLE_ABS:apnea` 142 (2026-11-16). A query written for PubMed therefore has its field tags translated into the Europe PMC field that holds the same thing, and a tag without one removed, its words left to match anywhere. The translation is [`toEuropePmcQuery`](../src/core/adapters/util.ts); Europe PMC's own syntax passes through unchanged. ChinaXiv and RussiaRxiv send words only: they ignore tags.

Each translation was checked on 2026-11-16 by comparing PubMed's `esearch` (counts, record ids and `querytranslation`) with Europe PMC restricted to `SRC:MED`. Pairs of counts below are PubMed, then Europe PMC; the full list is in the comment of the function. The field names are those of Europe PMC's fields web service and Appendix 1 of its Reference Guide (version 1.51, read from dev.europepmc.org; europepmc.org's own help pages answered 403).

Tags are also read in their long forms and aliases (`[Title/Abstract]`, `[Author]`, `[Publication Type]`, `[Journal]`, `[Language]`, `[Publication Date]`), in any case. The `dateRange` parameter is a different filter, but on Europe PMC it matches the same three date fields as `[dp]` (see [Dates](#dates)).

Removed, with their words left to match anywhere:

- **`[mh]`, `[mesh]` and every other tag with no translation.** Europe PMC has no MeSH field. `KW` holds MeSH headings and author keywords, and PubMed explodes a heading: `"Sleep Apnea Syndromes"[mh]` finds 50,220 records and `KW` 17,963 (with `tirzepatide[tiab]`, 54 and 2); only a heading with no narrower ones agrees (33,086, 32,313). Preprints carry no MeSH.
- **A tag after several unquoted words**, except `[au]` after a surname and initials and `[pt]` after the name of a publication type (`systematic review[pt]`). PubMed searches the words as a phrase only if its phrase index holds it ("will attempt to search those terms as a phrase", PubMed Help): `sleep apnea[tiab]` is the phrase `"sleep apnea"[Title/Abstract]`, but `creatine cognition[tiab]` is `creatine` mapped to MeSH and matched anywhere, AND `"cognition"[Title/Abstract]` (esearch, 2026-11-16). Quote the phrase (`"sleep apnea"[tiab]`) or tag each word.
- **A tag after a parenthesised group**, which PubMed ignores: `(tirzepatide OR semaglutide)[tiab]` has no `[Title/Abstract]` in its translation.
- **A quoted phrase with `*`**: Europe PMC ignores the `*` (1,048 records for `TITLE_ABS:"breast feed*"`, against PubMed's 15,911). A wildcard in a single word is kept when it has at least 4 characters before the first `*` (`diabet*[tiab]`: 960,599 records in PubMed, 942,328 in Europe PMC); Europe PMC answers HTTP 503 to a term that starts with `*`.
- **A modifier** (`[tiab:~3]`, `[pt:noexp]`) and a tag on a term the translation cannot read with certainty.
- A query that cannot be parsed (an unterminated quote, unbalanced parentheses) is sent without its tags.

A hyphenated word is quoted: unquoted, Europe PMC finds 232,653 records for `TITLE_ABS:il-6` and 193,835 for `TITLE_ABS:"il-6"` (PubMed: 195,634 for `il-6[tiab]`).

### Zero results

A search that finds nothing is no evidence of absence, and a model that gets a bare zero tends to drop words one call at a time. So when a page-1 search of **2 to 5 plain words** finds nothing in every database searched, and none failed, the server searches again without each word in turn, for the count only, and the warning names the word that blocks the query:

> `Without "Nilsen" the query matches 1 record in PubMed.`

That is the warning of `taurine slow-wave sleep Nilsen` searched in `pubmed`: without `Nilsen` the query has 1 record there, and without any of the other three words none (esearch, 2026-11-16). With several words and databases the clauses join, as in `Without "apnea" the query matches 12 records in PubMed and 40 in Europe PMC; without "tirzepatide", 3 in PubMed.` A word counts once however often it is repeated; "plain" means no quotes, parentheses, brackets (field tags), colons or `AND`, `OR`, `NOT`. When the `dateRange` or the `studyTypes`/`minDesignTier` filter is set, the counts are within it, and the warning ends ` within dateRange 2020 to 2021` or ` within the studyTypes/minDesignTier filter`. When leaving out any one word still matches nothing in every database probed, it says that instead: `Leaving out any one word still matches nothing in PubMed and Europe PMC, so two or more words are too specific together. This is not evidence of absence: try fewer, more general keywords.` (with `, or the dateRange is too narrow` and `, or no dateRange` when a `dateRange` is set). That statement needs an answer to every probe, so it is left out when a probe failed, and when a design filter is set, which explains the zero by itself. Where the probes say nothing, the warnings described above apply as before; where they do, they replace those of the databases and the generic one.

The probes cost requests and time. Each is a search without one word, for the count (`maxResults: 1`, page 1, the same filters), so a search of *n* words costs up to *n* more requests on each database, and such a search can take several seconds longer than one that finds something. All probes of a search get 10 seconds together; a probe that fails or runs out of time leaves its count unknown and is never an error. PubMed's requests are queued like any others; Europe PMC gets its probes at once. ChinaRxiv allows 30 requests a minute anonymously and 300 with an `X-API-Email` header (its [API specification](https://chinarxiv.org/api/openapi.json), checked 2026-11-16), so the probes of `chinaxiv` and `russiarxiv`, which share that allowance, go one at a time, stop at the first rate limit, and use at most a third of the minute's allowance: a database whose share can't take all its probes is left out of the probe. [How it works](how-it-works.md#zero-results-probing-the-words) has the details.

## `literature_fetch`

| Parameter | Type | Required | Notes |
| --- | --- | --- | --- |
| `ids` | `string[]` | yes | 1–50 database-specific ids, as `literature_search` returns them in `id`: PMIDs for `pubmed`; for `europepmc`, PMIDs, PMCIDs (the record comes back under its PMID) or prefixed ids for records outside PubMed, e.g. `CBA:644599` (Chinese Biological Abstracts) or `PPR…` preprints; for `chinaxiv` and `russiarxiv`, the ids `literature_search` returned. Each id is trimmed and must not be empty (an empty one is refused with a validation error). For `pubmed` and `europepmc` a PMID may also come as `PMID:9500320` or `MED:9500320`, or with leading zeros (`00009500320`), and is read as `9500320`. |
| `database` | `string` | yes | The database the ids belong to: `pubmed`, `europepmc`, `chinaxiv` or `russiarxiv`. Any other value is refused. |

Returns `{ articles, missing, warnings? }`: the records in the order requested, with `id` and `pmid` as in search results (see [`articles`](#literature_search)) and graded like them ([`studyType`, `designTier` and `flags`](#study-design-labels)), with the whole abstract, publication types, MeSH headings and retraction/correction links (`pubmed` and `europepmc`; ChinaRxiv has none). ChinaXiv and RussiaRxiv records are complete here, without the `abstractTruncated` mark; search results cut their abstracts at 500 characters. An id given twice, or spelled two ways (`9500320` and `PMID:9500320`), is fetched once and its record returned once, at the position of its first id. `missing` lists ids that couldn't be fetched, as they were sent (trimmed), so they can be matched up.

## `literature_fulltext`

| Parameter | Type | Required | Notes |
| --- | --- | --- | --- |
| `id` | `string` | yes | Id as `literature_search` returns it in `id`: a PMID, a PMCID (`PMC…`, a record's `pmcid`), an id of Europe PMC (`PPR…` preprints, and the ids of its other sources, which keep their prefix: `CBA:…`, `ETH:…`, `IND…`, patents such as `US2012071552`, `NBK…`), or a ChinaXiv or RussiaRxiv id (`chinaxiv-YYYYMM.NNNNN`, `ru-YYYYMM.NNNNN`); each works on its own. A bare number is a PMID, so `CBA:644599` must keep its `CBA:`. Any other id also needs `doi`. |
| `doi` | `string` | no | The record's DOI, `10.…` or a `https://doi.org/` link (`dx.` and `www.` too), from the `doi` field of a `literature_search` result; a `url` or `originalUrl` is not one. Needed only when `id` is one that Europe PMC has no record of: a URL there is refused with `INVALID_INPUT`, and a URL given with an id that resolves alone is ignored. A DOI given with an id that has a record (a PMID, a PMCID, any other id of Europe PMC) must be that record's: the record is read first (waiting for it at most 3 seconds), for the check and for the PMCID of a PMID, and another DOI returns `INVALID_INPUT` naming both (leave `doi` out, or pass the record's). Where the record has no DOI or can't be read in time, the DOI given is used, and the record, which can't say that DOI is its own, is left out of the warning of the DOI's text: the record of the DOI is looked up at Europe PMC for it instead, as it is for an id that names no record (any other id). A period, comma or semicolon at its end, as in a DOI copied out of a sentence, is dropped. With a PMCID or any Europe PMC id it is optional, since the DOI of Europe PMC's record is used without it, and that DOI opens the Unpaywall, proxy and direct steps below. |
| `offset` | `number` | no | Character position to return the text from: the previous call's `nextOffset`. Default `0`. |
| `maxChars` | `number` | no | The most characters to return. At most `MED_RESEARCH_FULLTEXT_MAX_CHARS` (default 50,000), which is also the default. |

Tries, in order: for a ChinaXiv or RussiaRxiv id, ChinaRxiv's translated text (see below); Europe PMC's full-text API, when the record has a PMCID (no email needed; tables come through row by row); the open-access copies Unpaywall knows; the institutional proxy, if configured; and the DOI directly. If none yields the article, it returns the abstract when the record has one, and no text otherwise: PubMed's for a PMID, for any other id the record's own from the database that holds it (Europe PMC's, looked up by exact id when it isn't cached; ChinaRxiv's for a ChinaXiv or RussiaRxiv id). Returns `{ id, doi?, source, fulltext?, format, truncated, totalChars?, nextOffset?, warning? }`, where `source` says which route worked (`europepmc`, `unpaywall`, `proxy`, `direct`, `chinarxiv`, or `none` for the abstract fallback) and `format` is `markdown` or `pdf` (plain text extracted from a PDF).

An id of Europe PMC (`PPR…`, `CBA:…`, `IND…`, a patent, …) is looked up at Europe PMC by its exact id, sent as it is. The record gives the abstract that comes back when there is no full text, and its DOI, which opens the Unpaywall, proxy and direct routes as for a preprint, so the id needs no `doi` of its own. When the record has no DOI (a patent's, a Bookshelf book's), the result is the abstract with a warning that says so and names the record's `url`, which a browser may open. An id of the other kinds (`CBA:…`, `IND…`, a patent, …) that Europe PMC has no record of (or can't be reached for, since the record is all there is to go on), given without a `doi`, returns `NOT_FOUND`. A `PPR…` id, like a PMCID, is `NOT_FOUND` only when Europe PMC answers that it has no record of it and no route found its text; if the record lookup fails or is rate-limited, the result is the fallback with its warning.

A long text comes in parts. `totalChars` is the length of the whole text; when more follows, `truncated` is `true` and `nextOffset` says where the next part starts, so a call with `offset: nextOffset` reads on. A part ends at a paragraph break, line break or space near its limit rather than mid-word, and the parts join up to the whole text. An `offset` past the end returns `INVALID_INPUT`. Every part comes from the text the first part came from: open-access texts are cached whole, and a proxy, direct or ChinaRxiv text is kept in memory while it is read, for 30 minutes after its last part, so later parts cost no download. The abstract fallback is cut to `maxChars` the same way, at a break near the end: `truncated` is `true` when it was cut, `totalChars` is the length of the whole abstract, and there is no `nextOffset`, because the abstract is never paged; the warning says it was cut and that `literature_fetch` returns it whole. With an `offset`, when the text can't be fetched again, the fallback returns no text, so that the abstract is never taken for the next part.

A web page counts as the full text only if it holds at least 2,000 characters besides its abstract, keywords, references and similar front and back matter. A paywalled article's page shows the abstract and little else, and so does arXiv's abstract page; those fall through to the next route. Sections a publisher's page adds that aren't the article, such as "Similar content being viewed by others" or "Cited by", are removed from the text.

`warning` opens with the article's standing when a record of it is known and carries a flag of `literature_search`: `RETRACTED:` (flag `retracted`, naming the linked notice's id when the record has it), `NOTICE:` (the record is a retraction notice, expression of concern or erratum, not a study) or `EXPRESSION OF CONCERN:` (flag `expression-of-concern`). It is set whether or not the text was retrieved, and read from the records at every call, never stored with a text: a text cached for 30 days is served with a retraction recorded after it was cached. A PMID's record is read before the text is looked for (PubMed's `esummary`, or the cache), since it gives the DOI and PMCID to fetch by; a PMID given with a `doi` waits for it at most 3 seconds, a PMID alone as long as it takes. When no cached record of the article exists and none is fetched anyway, one is asked for beside the text's own request, for a PMCID or any Europe PMC id (Europe PMC's record) and, for a text fetched by a `doi` that no record of the id confirms (an id that names no record, or a record without a DOI or one that couldn't be read in time), Europe PMC's record of the DOI, which is how a retracted paper is flagged when only its DOI is known; the text waits for it at most 3 seconds from the start of the call: an answer that fails or comes later is left out of the warning, never an error, and is kept for the next call. The record of the id doesn't speak for the text of a DOI it doesn't confirm: that text has the warning of the DOI's own record, or none. A later part of a text (`offset` above 0) asks for none of these; a PMID's record is the one the first call left in the cache. It uses the record as the databases report it at the time, so a missing warning doesn't prove that the paper isn't retracted: the flags of `literature_search` and `literature_fetch` are the authority.

When it falls back, `warning` then says what each route answered: no open-access copy, Unpaywall couldn't be asked (an HTTP error, a timeout, or turned off), the publisher refused access (HTTP 403, paywalled or blocking automated clients), the page held only the abstract, doi.org doesn't know the DOI, ChinaRxiv has no such page (HTTP 404; for a ChinaXiv or RussiaRxiv id given with a `doi`), and so on, with what to do about it. A DOI that doi.org doesn't know returns `NOT_FOUND` when there's no abstract to return either. So, given without a `doi`, does a ChinaXiv or RussiaRxiv id that ChinaRxiv answers 404 for, and a PMCID or `PPR…` id that no route found text for and Europe PMC answers that it has no record of (a real one without open-access text gets its abstract). An outage, a timeout or a rate limit says nothing of the id and stays a warning.

A ChinaXiv or RussiaRxiv id gets its text from [ChinaRxiv](#databases), a third-party service (`GET /api/v1/papers/{id}/text`), as `source: "chinarxiv"`, paged with `offset` and `maxChars` like any text. It is a machine translation into English, not the authors' wording, and `warning` says so on the successful result too: *Machine translation into English by ChinaRxiv, a third-party service, not the authors' wording: check numbers and claims against the original at \<originalUrl\> before relying on them.* An English original gets no note. When ChinaRxiv has no text for the record, the result is the record's abstract (whole, from `/papers/{id}`, cut to `maxChars` like any abstract fallback) with `source: "none"` and a warning: `ChinaRxiv has no text for this record.`, the translation note, and `ChinaRxiv wrote this abstract, not the authors.` where that applies. A call that finds nothing cached makes up to two requests to ChinaRxiv, the record and the text, with the same IP address, User-Agent and `X-API-Email` as a search. These texts are not put in the 30-day cache.

Copies that Unpaywall locates on PubMed Central or Europe PMC (articles and preprints) are fetched through Europe PMC's full-text API too, whose terms allow automated retrieval, instead of from those websites, whose terms don't. Pages are fetched only from public addresses: the tool refuses URLs and redirects that lead to loopback, private or link-local networks (such as cloud metadata endpoints), and bodies over 30 MB. When a refusal may be a fake-IP DNS proxy on the user's machine, the warning says how to allow it (`MED_RESEARCH_FULLTEXT_ALLOW_PRIVATE=1`, never on a shared server). Open-access texts (Europe PMC, Unpaywall) are cached for 30 days, under the source each was fetched from (the PMCID for Europe PMC's, the DOI for Unpaywall's) and never under the `id` given, and with the DOI they belong to, which is the `doi` of the result; texts from the proxy, direct or ChinaRxiv routes aren't cached at all. See [how-it-works.md](how-it-works.md#literature_fulltext).

**The proxy and direct routes can return licensed content.** The proxy route uses your institution's subscriptions, and so does the direct route (`https://doi.org/<DOI>`) when the machine is on a network with IP-based access. For subscription content, publisher terms often forbid use with AI tools unless your licence expressly allows it (Elsevier, for example: "You may not use Content from the Services in combination with an artificial intelligence tool … except as otherwise expressly permitted"), and they forbid systematic downloading. Configure the proxy only if your institution's licences permit this use, and don't let an agent fetch papers in bulk. The proxy works only if it lets the machine in without a login (on the campus network or VPN): the server sends no browser cookies.

## Databases

| Id | Source | Covers | Design labels |
| --- | --- | --- | --- |
| `pubmed` | NCBI E-utilities | PubMed / MEDLINE | Yes |
| `europepmc` | Europe PMC REST API | A mirror of PubMed, plus preprints (`PPR…`) and other sources such as Chinese Biological Abstracts (`CBA:…`). Words not limited by a tag are matched against the full text, so papers that only mention them match too (see [Tags on Europe PMC](#tags-on-europe-pmc)) | For MEDLINE-indexed records |
| `chinaxiv` | ChinaRxiv API (third party) | ChinaXiv preprints, machine-translated into English | No: always `unknown` |
| `russiarxiv` | ChinaRxiv API (third party) | Soviet-era papers, mostly mathematics, physics and chemistry; almost no medicine (25,456 records, machine-translated; most abstracts written by ChinaRxiv) | No: always `unknown` |

ChinaRxiv returns only records that contain every word of the query, in any order, and treats `AND` and `OR` as words: "vitamin" and "depression" each match ChinaXiv records, "vitamin depression" none. Search them with one or two key words; an empty result for a longer query comes with a warning saying so.

RussiaRxiv holds 25,456 Soviet-era records, mostly mathematics, chemistry and physics. A zero there is no sign that Russian medical research is missing: the one-word queries `sleep` matched 0 records, `rat` 2, `clinical` 11 and `water` 1,381 (ChinaRxiv API, 2026-11-16).

ChinaRxiv's API specification lists a third source, `crad`, besides `chinaxiv` and `russiarxiv`, but no record has it: `/stats` counts 26,652 ChinaXiv and 25,456 RussiaRxiv papers, which add up to its 52,108, and `source=crad` answers with a total of 0 (2026-11-16). A record of any other source would be dropped, not labeled ChinaXiv: `literature_fetch` reports its id as missing.

> **ChinaRxiv is not ChinaXiv.** [ChinaXiv](https://chinaxiv.org) is the Chinese Academy of Sciences preprint platform and does not publish a public API. `chinaxiv` and `russiarxiv` are served by [ChinaRxiv](https://chinarxiv.org), an independent project that machine-translates papers from ChinaXiv and other repositories into English (the Soviet-era papers appear on its sister site, SovietRxiv). It is not affiliated with the Chinese Academy of Sciences. Its records carry the flags `machine-translated` and, where ChinaRxiv wrote the abstract itself, `machine-generated-abstract`. Check the original record (`originalUrl`) before relying on a dose, population or outcome.

## Study design labels

Every `literature_search` result and `literature_fetch` article carries three fields, computed from database metadata only (plus a publisher's `RETRACTED:` title prefix, for the `retracted` flag), never by reading a design from the title or abstract. [How it works](how-it-works.md#the-grader-study-design-labels) has the full mapping, the reasoning and the sources.

- **`studyType`**: the design, from NLM PublicationType tags (PubMed, and Europe PMC, which mirrors them). Records without such tags are `unknown`: common for recent papers, journals outside MEDLINE, Europe PMC's preprints and `CBA:…` records, and every ChinaXiv and RussiaRxiv record. **Unknown means unlabeled, not weak.**
- **`designTier`**: how high the design ranks for "Does this intervention help?" by the [OCEBM 2011 Levels of Evidence](https://www.cebm.ox.ac.uk/resources/levels-of-evidence/ocebm-levels-of-evidence). When a label's definition spans levels, the lower one is used.
- **`flags`**: integrity notices and warnings.

| `designTier` | `studyType` |
| --- | --- |
| 5 | `meta-analysis`, `systematic-review`, **only if it pooled randomized trials**. Metadata rarely shows that, so only `Network Meta-Analysis` gets 5 |
| 4 | `randomized-controlled-trial` |
| 3 | `cohort` |
| 2 | `non-randomized-trial`, `clinical-trial`, `observational`, `case-control`, `cross-sectional` |
| 1 | `case-report`, `review` (not indexed as systematic) |
| 0 | `animal-study`, `in-vitro`, and any record flagged `retracted`, `notice`, `protocol` or `editorial` |
| `null` | `unknown`, and meta-analyses and systematic reviews whose pooled designs aren't indexed. **Unrated, not weak** |

`cohort`, `case-control`, `cross-sectional` and `in-vitro` are never assigned from metadata; they're labels for designs the model reads from an abstract.

| Flag | Meaning | Tier |
| --- | --- | --- |
| `retracted` | The paper was retracted | 0 |
| `notice` | A retraction notice, expression of concern or erratum: a notice, not a study | 0 |
| `protocol` | A trial protocol: planned, no results | 0 |
| `editorial` | An editorial or comment | 0 |
| `expression-of-concern` | The journal has published concerns about the paper | unchanged |
| `corrected` | An erratum exists; check the numbers you quote | unchanged |
| `updated` | A newer version exists, e.g. an updated Cochrane review; for a preprint, its published article, whose id `corrections` holds ([below](#preprints-and-their-published-versions)) | unchanged |
| `animals-not-humans` | MeSH lists animals but not humans; usually an animal study, but automated indexing sometimes drops the Humans tag | unchanged |
| `preprint` | Not peer reviewed | unchanged |
| `letter` | A letter, which may be correspondence or a short research report | unchanged |
| `machine-translated` | ChinaXiv/RussiaRxiv text machine-translated into English | unchanged |
| `machine-generated-abstract` | The abstract was written by ChinaRxiv, not the authors | unchanged |

Results are sorted with tiers 2–5 first, then `null`, then tiers 1 and 0, unless `sort` is `"date"`.

Two limits matter:

- **`designTier` ranks the design; it doesn't appraise the study.** Risk of bias, imprecision, inconsistency, indirectness and publication bias need the paper ([GRADE](https://pubmed.ncbi.nlm.nih.gov/21208779/)), and prognosis, diagnosis and harms questions rank designs differently (OCEBM). The skills cover this.
- **The labels are NLM's, but not hand-curated.** Since 2022, NLM indexes MEDLINE automatically, curating selected records by hand ([NLM 2021](https://www.nlm.nih.gov/pubs/techbull/nd21/nd21_medline_2022.html), [NLM 2024](https://www.nlm.nih.gov/pubs/techbull/ma24/ma24_mtix.html)). Treat a label as a strong prior to confirm when it matters.

### Preprints and their published versions

A preprint and the journal article it became are two records, each with its own DOI, so they are not merged. `corrections` links them both ways, with the names PubMed uses (`UpdateIn`, `UpdateOf`):

| Record | `corrections` | `flags` |
| --- | --- | --- |
| The preprint, when it has a published version | `{ type: "UpdateIn", id: <the article's id> }` | `updated` |
| The published article | `{ type: "UpdateOf", id: <the preprint's id> }` | none for this link: nothing is wrong with the newer record |

So when a preprint is flagged `updated`, cite the published article (its id is in `corrections`), fetching it with `literature_fetch` if needed. The `id` of a link is in the form of its database: a PMID, or a Europe PMC id such as `PPR1312266`. Europe PMC's "Preprint of" (on the preprint) and "Preprint in" (on the article) are mapped to `UpdateIn` and `UpdateOf`, as are its "Update in" and "Update of", which carry PubMed's own pairs. Checked on 2026-11-16:

- **PubMed.** PMID 42238413 (a preprint) has `UpdateIn` with PMID 42745487, whose record has `UpdateOf` with 42238413. Of 300 preprints with an `UpdateIn` link none had another link type, every target was a record without the Preprint type, and every target held the `UpdateOf` back. `preprint[pt] AND hasupdatein` finds 42,493 of the 72,073 preprints, `preprint[pt] AND hasupdateof` none.
- **Europe PMC.** PPR1312266 has `{ source: "MED", id: "42905201", type: "Preprint of" }` and 42905201 `{ source: "PPR", id: "PPR1312266", type: "Preprint in" }`. All 57 preprints of `SRC:PPR AND HAS_PUBLISHED_VERSION:y AND tirzepatide` and all 179 articles of `HAS_PREPRINT:y AND tirzepatide AND SRC:MED` carry one.

Two cautions. Many of Europe PMC's links are its own matches, not asserted by the preprint server: the `note` Europe PMC gives a link names the origin (`CrossRef Pre-print loader`, `Link created based on a title-first author match`, `Link created based on another matching version of this preprint`), and 806 of the first 1,000 preprints with a published version were matches; the server keeps all the links; the titles of 149 of 150 such pairs were identical, one similar. The article side lists one preprint where several versions link to it (three PsyArXiv versions link PMID 42950493, which lists one). And `UpdateOf` is NLM's link to "the article being updated" (its element descriptions do not mention preprints), so in PubMed it can also point to an earlier version of a review rather than to a preprint. A preprint that PubMed holds is also in Europe PMC under two ids (MED 42238413 and PPR1237523, one DOI), so its article lists both. When two databases return the same DOI in one search, the copy kept also gets the links of the other.

## Errors

A failing tool returns an `isError` result whose text holds this payload (`UNKNOWN` for unexpected errors). Parameters the schema rejects (an unknown database, an empty query, `maxResults` over 50, a `page` below 1, above 10,000 or not an integer) come back as an `isError` result with the validation message instead. `literature_search` fails only when every database it searched failed, or on input it refuses; `literature_fetch` lists ids it couldn't fetch in `missing`, and fails outright only when a PubMed request fails (unreachable, or rate-limited).

```ts
{
  code: "RATE_LIMIT" | "QUERY_TOO_BROAD" | "PARSE_FAILURE" | "NETWORK_ERROR" | "TIMEOUT" | "NOT_FOUND" | "INVALID_INPUT";
  message: string;      // human-readable, for logs
  userMessage: string;  // actionable phrasing for the agent or user
  recoverable: boolean; // whether retrying or adjusting can succeed
  retryAfter?: number;  // seconds to wait before retrying (rate limits)
}
```

| Code | When | What to do |
| --- | --- | --- |
| `RATE_LIMIT` | A database kept answering 429 after two retries, or asked for a wait over 5 seconds; the message names it | Wait `retryAfter` seconds. For PubMed, set `NCBI_API_KEY` |
| `QUERY_TOO_BROAD` | Library calls only: a PubMed client built with a `broadThreshold` refused a search matching more than that many records (in a multi-database search: a warning). The MCP server sets none: a query over 10,000 records is served, with a warning that names the count | Add `[tiab]` or `[mesh]` terms or `AND` clauses |
| `PARSE_FAILURE`, `NETWORK_ERROR` | The database was unreachable or answered something unreadable. A server error (HTTP 500, 502, 503, 504), a timeout or a dropped connection has already been retried twice, within 20 seconds | Retry once, then report the database as unreachable |
| `TIMEOUT` | On the HTTP server, a search or fetch used up its 30 seconds: before a request could be sent, while waiting for an answer, or before a retry. Typically a deep `sort: "date"` page | Retry. A deep search page keeps the work already done, so each retry gets further, and the deepest date pages can take several. If retries stop getting further, ask for an earlier page or narrow the query |
| `NOT_FOUND` | `literature_fulltext` got an id it can't resolve (no such PMID; an id of none of the kinds it looks up, one Europe PMC has no record of, a PMCID or `PPR…` id no route found text for and Europe PMC answers it has no record of, or a ChinaXiv or RussiaRxiv id ChinaRxiv has no record of, without a `doi`), or a DOI doi.org doesn't know and there's no abstract to return | Check the id (a prefixed id keeps its prefix), or pass the `doi` of the search result |
| `INVALID_INPUT` | A query with no search term (only punctuation, operators or field tags: `()`, a lone `"`, `*`, `NOT`, `[tiab]`), or one PubMed can't read (its "Empty Term" and parser errors); a date that doesn't exist, or `from` after `to`; a `page` starting past the 10,000th record of a search; a full-text `offset` past the end of the text; a `doi` that isn't one (a record's `url`, say) where the id needs one; a full-text `doi` that isn't the DOI of the record of the PMID, PMCID or other id of Europe PMC it was given with; in library calls also an unknown database, an empty query or a `page` below 1 or not a whole number (the MCP schema refuses those itself) | Correct the parameter the message names |

In a multi-database search, a database that fails while others answer becomes a warning, `<database> search failed: <message>`, not an error.
